# 70분 워크숍 진행안

대상: EVM·Solidity·JSON-RPC 경험이 있는 은행/핀테크 엔지니어. 목표는 PCL 정책 거절과 내 컴퓨터에서의 비공개 지급을 실행하고 두 환경의 증거·공개 범위를 구분하는 것입니다.

## 사전 준비

Node·Git·테스트 토큰·Docker를 준비하고 Privacy 소스 빌드와 개발용 증명 생성 파일 생성은 수업 전에 끝냅니다. 공개 테스트 계정은 동시 사용과 잔액을 보장하지 않으므로 참가자별 별도 계정이 권장됩니다. 운영자 키와 원본 privacy 로그는 화면에 띄우지 않습니다.

| 시간 | 설명·실습 | 성공 기준 |
|---|---|---|
| 0–8분 | 카페 A→원두업체 B 상황, 은행 승인과 체인에 기록된 정책의 경계 | 기존 은행 업무와 실습 역할 구분 |
| 8–15분 | EVM·프리컴파일, OKRW, PCL·EAS·Privacy, 프록시 구조 | 요청→정책→구현체 순서 이해 |
| 15–34분 | 파일 01–04 실행 | 정상 status 1 / 차단 status 0 |
| 34–40분 | 첫 지급과 차단 후 추가 지급 비교 | 차단 후 잔액/횟수 불변 |
| 40–47분 | 비공개 잔액·증명 생성·공개 정보·감사 권한 | 로컬과 Maroo 차이 설명 |
| 47–62분 | deposit→transfer→list-notes | Alice 3 / Bob 7 / 반복 조회 일치 |
| 62–63분 | 두 실습의 세 가지 기대 결과 비교 | 정상 지급·차단·비공개 잔액 확인 |
| 63–68분 | 핵심 토론 질문 4개 | 정책 적용 경로·정보 공개 권한·원화 비용 관리 설명 |
| 68–70분 | 참고 링크, 각 조직의 적용 조건 | 후속 검증 항목 선택 |

70분은 계획값이며 전체 참가자 리허설 시간은 측정하지 않았습니다.

## 이해도를 확인하기 위한 토론 질문 · 63–68분

첫 번째와 두 번째 질문에 각각 1분 30초, 세 번째에 30초, 네 번째 PoC 질문에 1분 30초를 배정합니다. 네 번째는 1~2명의 제안을 듣고 나머지 참가자는 짧게 기록합니다. 먼저 참가자의 답변을 듣고 아래 방향으로 보완합니다. 용어를 외웠는지보다 은행 업무에 연결해 이유를 설명할 수 있는지 확인합니다.

### 1. 은행 서버에서 이미 지급 조건을 검사하는데, 체인에서도 정책을 검사하면 무엇이 달라질까요?

**답변 방향:** 서버 검사는 그 서버를 거치는 요청을 통제합니다. 체인에서의 검사는 해당 정책이 적용되는 실행 경로를 통제합니다. 앱을 거치지 않은 직접 호출도 이 경로를 통과한다면 정책을 적용할 수 있습니다. 따라서 다른 진입점이나 구현체 직접 호출로 우회할 수 있는지 확인해야 합니다. PCL이 있다는 이유만으로 체인의 모든 전송에 같은 정책이 자동 적용되는 것은 아닙니다.

**확인할 이해:** 앱의 승인과 체인의 실행 통제를 구분하고, 정책의 적용 범위와 우회 경로를 설명하는가.

**후속 질문:** 카페 A가 은행 앱 대신 컨트랙트를 직접 호출하면, 어느 지점에서 요청을 막아야 할까요?

### 2. 거래 금액을 공개하지 않으면서도, 부정한 지급을 막고 필요한 감사를 할 수 있으려면 무엇이 필요할까요?

**답변 방향:** 지급의 유효성은 증명 검증으로, 서비스 이용 조건은 정책 검사로, 필요한 정보의 열람은 권한에 따른 공개로 나누어 생각합니다. 누가 어떤 조건에서 어떤 정보를 볼 수 있는지 정해야 합니다. Privacy가 모든 규제 조건을 자동 검사한다거나, 지급 권한이 곧 정보 열람 권한이라는 답변은 바로잡습니다.

**확인할 이해:** Privacy·Policy·Disclosure의 역할을 구분하고, 거래 당사자·정책 관리자·정보 열람자의 권한을 구분하는가.

**진행자 유의:** 이번 로컬 실습은 비공개 지급과 수취 조회입니다. PCL과 연결한 Maroo Privacy 지급이나 감사자 정보 열람을 실행했다고 설명하지 않습니다.

### 3. 수수료를 OKRW로 내면 은행의 비용 관리에서 무엇이 쉬워지고, 무엇은 여전히 변할까요?

**답변 방향:** 원화 기준으로 예산과 비용을 관리할 수 있고, 별도 가스용 암호화폐의 가격 변동 부담을 줄일 수 있습니다. 네트워크 사용량과 거래의 연산량 등에 따른 수수료 변화는 남습니다. 원화 기준 비용 관리가 고정 수수료를 뜻하지는 않습니다.

**확인할 이해:** 비용의 표시·관리 기준과 수수료 크기를 결정하는 요인을 구분하는가.

### 4. 우리 업무에 적용한다면 어떤 PoC가 가능할까요?

**답변 방향:** 대상 업무 하나를 고르고, 필요한 지급 조건·정보 공개 범위·성공 기준을 제시합니다. 예를 들어 기업 지급 중지 PoC에서는 허용된 지급의 완료와 차단 계정의 직접 요청 거절, 추가 잔액 변화가 없음을 확인할 수 있습니다. 비공개 정산 PoC에서는 수취 결과와 권한별 정보 열람을 확인할 수 있지만, Maroo에서의 실행 준비와 정책 연결·감사 권한은 추가 검증이 필요합니다.

**확인할 이해:** 기능 이름을 나열하는 데 그치지 않고 업무 문제를 검증 가능한 성공·실패 조건으로 바꿀 수 있는가. 이미 실행한 범위와 추가 준비가 필요한 범위를 구분하는가.

**후속 질문:** 어떤 결과가 나오면 성공이고, 어떤 결과가 나오면 도입을 보류하겠습니까?

참가자는 치트시트의 완성 예시를 파일의 주석 블록 대신 붙여 넣습니다.

서비스 장애 시에는 거래 처리 결과 JSON과 로컬 결과를 열어 **기존 실행 기록**이라고 밝히고 상태 변화를 설명합니다. 실시간 실행을 한 것처럼 연출하지 않습니다. 상세 대응은 [오류 해결](TROUBLESHOOTING.md)에 있습니다.

워크숍 이후 각 조직은 후속 PoC에서 관리자·발급자 권한, 키 보관·관리, 공개 정보, 감사자 접근권한, 테스트넷에 맞는 증명 자료와 입력 데이터 준비 방법, 장애 재처리 기준을 검증합니다. 별도 마무리 강의를 늘리기보다 후속 검토 메모로 제공합니다.
